基于项目文档中的 Go 代码结构（`main.go` + `internal/app` 绑定层 + `internal/mdv` 领域层 + `tools/genicon`），结合 Wails v3 的官方架构实践，给出以下分析与调整建议。
---
## 一、包名调整建议
| 现状 | 问题 | 建议 |
|---|---|---|
| `internal/mdv` | 包名是项目缩写（mdview），既与项目重名又不表意；11 个文件横跨 settings/history/favorites/文件树/编码检测/图片服务/导出/关联 7+ 个领域，严重违反单一职责 | 按领域拆包（见下节）；若暂不拆，至少改名 `internal/core` 占位 |
| `internal/app` | 名字尚可，但混入了 `clipboard_*`、`procpid_*` 这类系统能力，不是"绑定层"的职责 | 保留 `app` 只放绑定；系统能力下沉到 `internal/win` 或 `internal/sysutil` |
| `*_other.go` | `_other` 不是 Go 的魔法后缀，**必须**配 `//go:build !windows`，否则非 Windows 平台重复定义 | 确认 build tag 存在；既然项目只支持 Windows，可考虑直接删除 `_other` 文件减少维护面 |
| `mdv_test.go` | 单个测试文件覆盖整个包，定位困难 | 按被测文件拆分：`assoc_test.go`、`settings_test.go`、`readfile_test.go`、`imgserver_test.go`、`export_test.go`，用表驱动测试 |
| `tools/genicon/main.go` | — | 保持，补齐注释与 `-h` 用法说明即可 |

## 二、包结构调整
### 目标结构（方案 B：按领域拆分）
```
go-mdview/
├── main.go                    # 只做装配：wails 应用构建、service 注册、CLI 参数
├── internal/
│   ├── app/                   # 绑定层（薄）：参数校验 + 错误映射，无业务逻辑
│   │   └── services...        # 按域拆成多个 Wails service（见第三节）
│   ├── win/                   # 平台能力：clipboard、procpid（单实例）、assoc
│   ├── storage/               # 统一持久化：JSON/YAML、原子写、锁（store.go + yamlfile.go 合并）
│   ├── settings/              # settings.go
│   ├── fsops/                 # fsops.go + readfile.go（编码检测）
│   ├── imgsrv/                # imgserver.go
│   ├── exporter/              # export.go
│   └── watcher/               # watcher.go
└── tools/genicon/
```
**依赖方向原则**：`main → app → 领域包`；领域包之间禁止横向 import，需要协作时由 `app` 层编排或通过接口注入（接口定义在消费方，Go 惯例）。
### 两个关键的结构性优化（Wails v3 特性）
1. **`App` 上帝对象拆成多个 service**。`api.ts` 里 43 个方法一个大接口，Go 侧一个 struct 全实现。Wails v3 官方推荐按域注册多个 service，bindings 会自动按 service 名分目录生成：
```go
application.New(application.Options{
    Services: []application.Service{
        application.NewService(NewFileService(reader, watcher)),
        application.NewService(NewSettingsService(store)),
        application.NewService(NewWindowService(...)),
        ...
    },
})
```
注意：拆分后需重跑 `wails3 generate bindings -ts -d frontend/bindings`，并同步 `api.ts` 的 import 路径（README 已写明绑定是生成物，改包名后必须重新生成，否则运行时找不到 `App.*`）。
2. **`imgserver.go` 迁移到 Wails v3 Service Route**。v3 的 service 可直接挂 HTTP 路由（`ServiceOptions.Route: "/mdimg"` + 实现 `ServeHTTP`），复用应用内置 asset server（`http://wails.localhost/mdimg/...`）。好处：
    - 不再自行监听 localhost 端口 → 无端口冲突、无被本机其他进程扫描访问的攻击面
    - 生命周期由 Wails 管理，`StopWatch`/手动 shutdown 之类的手动清理 API 可以删掉

## 三、绑定层（App.\*）的具体问题
1. **`GetLastError()` 是反模式**。"全局最后错误"在并发绑定调用下会互相覆盖、时序不可靠。Wails 绑定方法支持 `(value, error)` 返回，前端 Promise 直接 reject 拿到错误 → 删除 `GetLastError`，每个方法返回 `error`。
2. **错误需要类型化**。前端文案区分了 `toast.fileMissing`、`error.tooLarge` 等，说明前端需要判别错误类型 → Go 侧定义 sentinel error（`ErrFileMissing`、`ErrTooLarge`），用 `fmt.Errorf("...: %w", err)` 包装，前端按错误码映射文案。
3. **`SaveMarkdown(path, content, encoding)` 不应信任前端传 encoding**。encoding 应由 `ReadMarkdown` 时服务端记录（内存 map[path]encoding），Save 时取服务端记录；至少把字符串参数类型化为枚举常量，防止前端传任意值。
4. **冗余方法合并**：
    - `FindByTitle` / `FindByTitles` → 保留 `FindByTitles` 返回数组，前端取第一个即可；
    - `ListTree` / `RefreshTree` → 合并为带 `force` 参数或引入缓存失效策略；
    - `StatFile` 语义是"存在与否" → 按惯例改名 `FileExists`。
5. **`AllowImageDir(dir)` 状态型 API 有时序隐患**（前端忘调/乱序就 404）→ 改为 `ReadMarkdown` 成功后服务端自动授权其所在目录，删掉该 API。
6. **`WindowPin/WindowMin/...` 等窗口方法**：核对 `@wailsio/runtime` 前端 API 是否已覆盖（v3 runtime 提供窗口操作），避免重复造轮子；确实需要 frameless 场景定制的才保留绑定。

## 四、各模块问题分析与优化
### `imgserver.go`（安全重点）
- `/mdimg/{hex(绝对路径)}/{filename}` 中 hex 可逆、URL 可伪造——**真正的安全边界必须在服务端**：
    - `filepath.Clean` 后做严格的授权目录前缀校验，防 `..` 穿越、防符号链接逃逸；注意 Windows 大小写不敏感和 8.3 短文件名（`PROGRA~1`）绕过前缀比较的问题（用 `filepath.EvalSymlinks` / `syscall.UTF16FromString` 归一化后再比较）；
    - `Content-Type` 按扩展名白名单映射，加 `X-Content-Type-Options: nosniff`；
    - 大文件用流式（`http.ServeContent`），限制并发与响应大小。
- 若保留独立监听（未迁移 service route）：只绑 `127.0.0.1` + 随机端口 + 校验 Host 头。
### `readfile.go`（编码检测与原子保存）
- 检测顺序建议：BOM（UTF-8/UTF-16LE/BE）→ 严格 UTF-8 校验（`utf8.Valid`）→ GB18030 兜底。GBK/GB18030 解码几乎不会失败，所以防误判的关键在 UTF-8 阶段的**严格**校验；顺带考虑 Windows 记事本旧版产出的 UTF-16 文件。
- 原子替换：临时文件写在**同目录**（保证同盘 rename）→ 写完 `f.Sync()` → `os.Rename`。Go 在 Windows 上 Rename 支持覆盖，但杀软/占用会偶发失败，需要重试与失败时清理 tmp 文件；换行符 CRLF/LF 保持原样不要静默归一化。
### `watcher.go`
- Windows 文件事件会风暴（编辑器原子保存 = write+rename 双事件）→ 必须**防抖**（200~500ms 窗口）+ `mtime+size` 或内容哈希比较，避免无变化重载；
- 递归 watch 大 vault 注意句柄数量与 `node_modules` 排除与文件树遍历共用同一份排除清单；
- `StopWatch()` 出现在前端 API 中说明清理依赖前端调用 → 改为 `ServiceShutdown` 钩子里统一关闭（v3 生命周期管理，退出逆序执行）。
### `settings.go` / `store.go` / `yamlfile.go`
- 四份持久化（settings/history/favorites.json + mdview.yml）→ 抽一个 `storage` 抽象：原子写（tmp+rename+备份）+ 文件锁；
- **并发**：Wails service 是单例、并发共享（官方文档明确要求加 mutex）→ 所有读改写（尤其 `SaveSettings`、`ToggleFavorite`）在 `RWMutex` 写锁内完成；
- `useYaml` 切换语义要明确为单向迁移（yaml 生效后 json 冻结），避免双向同步漂移。
### `assoc_windows.go`（注册表关联）
- **不要写 `FileExts\.md\UserChoice`**——Win10+ 该键有系统哈希校验，程序写入不生效且可能被判定篡改。正确做法：只写 `HKCU\Software\Classes` 的 ProgID（`mdview.markdown`）+ `OpenWithProgids`，再用 `SHOpenWithDialog` 或引导用户到系统设置确认；
- `shell\open\command` 的参数**必须带引号** `"...mdview.exe" "%1"`，防空格路径与参数注入；
- "还原关联前默认程序"需要关联前备份旧 ProgID/命令——备份存哪、如何校验（程序被卸载后残留）要想清楚。
### `procpid_windows.go`（单实例）
- 推荐方案：`CreateMutexW` + `ERROR_ALREADY_EXISTS` 判定，用命名管道把启动参数（文件路径，UTF-16）转发给已有实例；pid 文件方案有 stale 残留风险，必须校验进程存活；
- `RestartApp` 要小心：新进程 spawn 后老进程延迟退出，避免互斥体未释放导致新实例被单实例检查拒绝。
### `clipboard_windows.go`
- `OpenClipboard` 失败需重试（被其他进程占用很常见）；`GlobalLock/Unlock`、`CloseClipboard` 严格配对防泄漏；
- `CopyImage`（dataURL）→ 解出 PNG 后优先注册 `CF_PNG` 格式 + `CF_DIBV5` 兜底，兼容更多目标应用。
### `export.go`
- 导出 HTML 里若仍引用 `/mdimg/...` 回放 URL，文件离开应用就全部裂图 → 导出时把本地图片内联为 data URI 或复制到导出文件旁用相对路径。
### `fsops.go`
- 用 `filepath.WalkDir`（Go 1.16+，比 Walk 快、少分配）；
- `FindByTitle` 递归扫描在大 vault 下慢 → 首次遍历时建 `map[title]path` 索引，watcher 事件增量更新。
### `main.go`
- 瘦身为纯装配层；多文件拖放只取第一个（与前端 `drop.openFirst` 语义对齐）；
- `BuildInfo()` 用 `-ldflags "-X main.version=..."` 注入 git rev/date，不要硬编码。

## 五、通用工程化建议
1. **错误与日志**：统一 `slog` 结构化日志写 `%AppData%\mdview\logs\`；错误一律 `%w` 包装带上下文（`fmt.Errorf("read %s: %w", path, err)`）。
2. **context**：长操作（目录遍历、导出）接受 `ctx`；`ServiceStartup(ctx, ...)` 的 ctx 保存下来用于取消后台 goroutine。
3. **测试与 CI**：README 的 `go vet ./...` 升级为 `golangci-lint`（govet + staticcheck + errcheck + **gosec**——对 imgserver、注册表、剪贴板这些敏感面特别有价值）；Linux CI 跑不了 Windows 单测，至少加 `GOOS=windows go vet ./...` + `go build` 做编译级回归。
4. **文档/配置一致性**：README badge 写 "Go 1.27+"——Go 工具链目前不存在 1.27（最新为 1.25），若 `go.mod` 真写了不存在的版本会导致工具链下载失败、编译直接报错，建议核对改为实际所需版本。

## 六、优先级建议
| 优先级 | 事项 |
|---|---|
| **P0** | 移除 `GetLastError`；imgserver 安全加固（路径归一化校验/迁移 service route）；原子保存的失败路径审查；注册表不写 `UserChoice`；有状态 service 补锁 |
| **P1** | `App` 按域拆 service（连带重新生成 bindings + 改 `api.ts`）；`mdv` 拆包；watcher 防抖；错误类型化；`AllowImageDir`/encoding 参数等 API 语义修正 |
| **P2** | 测试文件拆分 + golangci-lint/CI；`FindByTitle` 索引；导出图片内联；命名清理（`StatFile`→`FileExists` 等）；文档勘误 |
总体评价：三层结构（main → app → mdv）方向正确，主要问题是 `mdv` 包职责过重、`App` 绑定对象过大，以及 imgserver/编码保存/注册表关联这几个安全与正确性敏感点需要加固。结构调整成本不高（领域文件间耦合低），建议按 P0 → P1 顺序推进。
